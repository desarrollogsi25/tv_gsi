## 4. Evidencia de Intercepción Previa a Mutaciones

1. **Protección en Router Administrativo:**
   En el stack del router de Express para `DELETE /api/admin/screens/:uuid`, la capa de autorización `requireRole('admin')` se sitúa estrictamente antes del controlador de eliminación (`L288`). Al invocarla con credenciales de `viewer`, el flujo se aborta de inmediato emitiendo HTTP 403, garantizando que ninguna transacción `BEGIN`, query `FOR UPDATE` o eliminación en `nexus_tv.tv_screens` llegue a ejecutarse.
2. **Protección ante Streaming Multipart en Media:**
   En `POST /api/tv-content/upload`, `requireRole('admin', 'editor')` precede a `upload.single('mediaFile')`. Un usuario con rol `viewer` es rechazado con HTTP 403 antes de que Multer abra streams hacia el disco o buffer de memoria para archivos de hasta 500 MiB.
3. **Consistencia en Capa WebSocket:**
   En `src/sockets/index.js`, la conexión administrativa al namespace `/control` valida `socket.data.user.role === 'admin'`. Adicionalmente, el manejador de eventos `admin:send_command` verifica explícitamente el rol antes de retransmitir comandos a las salas de pantallas.

## 5. Riesgos Residuales Identificados
* **RSK-025 (Suplantación de Pantallas en `/control`):** Las pantallas TV se conectan al namespace `/control` mediante query string `?tv_uuid=...` sin presentar un token criptográfico de pantalla firmado. Este riesgo pertenece a la arquitectura de identidad de pantallas cliente y no a RBAC de usuarios administrativos, permaneciendo en seguimiento específico.
