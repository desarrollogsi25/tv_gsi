## 3. Evidencias Técnicas

### 3.1. Cron Job 1: Auditoría de Pantallas Inactivas (L14-29)
* **Expresión Cron:** `*/15 * * * *` (Cada 15 minutos).
* **Consulta SQL:**
  ```sql
  SELECT count(*) FROM nexus_tv.tv_screens 
  WHERE is_active = true 
    AND (last_login IS NULL OR last_login < NOW() - INTERVAL '10 minutes');
  ```
* **Impacto Operativo:** Inofensivo / Solo Lectura. Emite un `console.log` informando el número de pantallas sin actividad en los últimos 10 minutos. No muta estados en BD ni cierra sockets.

### 3.2. Cron Job 2: Limpieza de Archivos Huérfanos (L32-59)
* **Expresión Cron:** `0 3 * * *` (Diario a las 03:00 AM).
* **Mecánica del Algoritmo:**
  ```javascript
  const dbFilesRes = await pool.query("SELECT source_url FROM nexus_tv.content WHERE source_type = 'local_file'");
  const activeFiles = new Set(dbFilesRes.rows.map(r => path.basename(r.source_url)));

  const diskFiles = fs.readdirSync(mediaDirectory);
  for (const file of diskFiles) {
      if (!activeFiles.has(file)) {
          const fullPath = path.join(mediaDirectory, file);
          fs.unlinkSync(fullPath);
      }
  }
  ```
* **Destino de Borrado:** Borra **físicamente del disco** (`/app/media`). **NO borra registros de la base de datos**.

### 3.3. Evaluación de Casos Específicos

#### A. ¿Qué ocurre si un archivo acaba de subirse y aún no se asignó a una playlist?
* En [src/routes/media.js](file:///c:/Users/DEVELOPMENT/Downloads/tv_gsi/src/routes/media.js#L75-L100), la subida de archivos ejecuta inmediatamente `INSERT INTO nexus_tv.content (title, source_url, source_type, ...) VALUES (...)`.
* El cron consulta `SELECT source_url FROM nexus_tv.content` (biblioteca global), **no** la tabla de playlists (`nexus_tv.playlist_content`).
* **Conclusión:** El archivo **NO es eliminado**, incluso si permanece días o semanas en la biblioteca sin asociarse a ninguna pantalla o lista.

#### B. Condición de Carrera en Subidas Activas (Upload In-Flight Race Condition)
* Multer escribe el archivo en disco (`mediaDirectory`) mientras recibe el flujo de bytes de la petición multipart.
* Si un operador o proceso automático sube un archivo de gran tamaño (ej. video de 250 MB) o FFprobe está calculando la duración a las `03:00:00 AM`:
  1. El archivo ya existe en disco (`diskFiles`).
  2. La fila en `nexus_tv.content` aún **no ha sido insertada** porque la petición HTTP no ha finalizado.
  3. El cron determina que el archivo no está en `activeFiles` y ejecuta `fs.unlinkSync(fullPath)`.
  4. La petición HTTP de subida falla posteriormente con error de sistema de archivos (`ENOENT`) o inserta un registro en BD apuntando a un archivo recién borrado.

#### C. Inconsistencia Referencial Inversa (Omisión de Limpieza en BD)
* El cron solo limpia `Disco - BD`.
* **Nunca valida `BD - Disco`:** Si un archivo desaparece del disco (como los 28 archivos 404 del bug **BUG-002**), el cron no detecta ni depura las filas huérfanas en PostgreSQL, perpetuando el error de reproducción.

## 4. Conclusión y Clasificación

* **Clasificación:** ⚠️ **APROBADO CON OBSERVACIONES (Riesgo de Concurrencia Registrado)**
* **Riesgo Asociado:** **RSK-019** (`docs/13-testing/risk-register.md`).
* **Severidad:** **Media**
* **Prioridad:** **P2**
* **Recomendación de Mitigación:**
  1. Añadir margen de gracia temporal en disco: no borrar archivos cuya fecha de modificación (`mtime`) sea menor a 1 o 2 horas (`Date.now() - stat.mtimeMs < 7200000`).
  2. Implementar una tarea de reconciliación inversa que marque o alerte sobre registros en `nexus_tv.content` cuyos archivos falten físicamente en disco.
