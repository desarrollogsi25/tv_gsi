## 4. Análisis Arquitectural del Comportamiento Offline

### 4.1. Mecánica de Entrega en el Backend ([src/routes/admin.js](file:///c:/Users/DEVELOPMENT/Downloads/tv_gsi/src/routes/admin.js), L214-233)
```javascript
router.post('/screens/:uuid/control', (req, res) => {
    const { uuid } = req.params;
    const { command, payload } = req.body;

    if (!command) {
        return res.status(400).json({ success: false, message: 'Comando requerido.' });
    }

    if (!controlNamespace) {
        return res.status(503).json({ success: false, message: 'Hub de control no inicializado.' });
    }

    if (uuid === 'all') {
        controlNamespace.emit('command:execute', { command, payload: payload || {} });
    } else {
        controlNamespace.to(`tv:${uuid}`).emit('command:execute', { command, payload: payload || {} });
    }

    res.json({ success: true, message: `Comando '${command}' enviado correctamente.` });
});
```

### 4.2. Hallazgos Arquitecturales y Resiliencia
1. **Emisión en Salas Vacías en Socket.IO:**
   * En la arquitectura de Socket.IO, `controlNamespace.to('tv:' + uuid).emit(...)` busca el adapter de la sala. Si no hay ningún socket activo asociado a la sala `tv:<uuid>`, la emisión se descarta en memoria de forma segura y transparente sin lanzar excepciones.
   * Esto garantiza que el backend **nunca crasheará ni generará un error 500** por enviar comandos a pantallas apagadas o desconectadas.
2. **Ausencia de Cola de Mensajes Persistente (No-ACK):**
   * El comando tiene naturaleza "fire-and-forget". Si la pantalla se encuentra apagada en el momento del envío, el comando se pierde y no será ejecutado al encenderse la TV más tarde.
   * En el caso de `reload`, esto es en realidad un comportamiento deseado (evita tormentas de recargas cuando las pantallas se reconectan tras caídas de red masivas).
3. **Respuesta HTTP 200 Administrativa:**
   * La API devuelve HTTP 200 informando que el comando fue enviado al hub de control. No garantiza entrega física en el cliente si este está desconectado.
